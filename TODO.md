- [x] **Slowdown, as the arcade has it** (owner: a PRIORITY, "this project has to have it"). On the board the 68000 (16 MHz) gets one VBLANK's worth of cycles (278,016) for each frame of the game; a frame whose work runs longer misses the VBLANK and the game waits a whole frame more: the slowdown. Done, exact against MAME's 68000:
  - The decompiler (`tools/core`, now the fork `CapsLock4284/arcade-decomp`, branch `timing-model`; the profile's `TIMING_MODEL`) puts `m68k_block(cycles, point)` after every instruction of the C: its 68000 cycles (the Motorola tables, checked against MAME's core; a branch's longer way and the data's part of MULU/MULS/DIVU/DIVS and shifts by a register added at run time with `m68k_cycles`) and its interrupt point (where its microcode samples the interrupt lines, from MAME's m68000.lst: a VBLANK that came by then is taken at the instruction's end, a later one after the next instruction)
  - The runtime (`runtime/src/game_program.c`, `game/support.h`) keeps the board's time; the VBLANK comes where the count says, in the middle of the work if it runs long: the port gets its frame there (the last picture again), the interrupt runs the sound, `frame_counter` and `random_index`, and `wait_for_frame` waits the extra frame by itself. The wait loop goes round for real (each round steps `random_index`, so the idle time is part of the random numbers)
  - Checked: `tools/cref/cref_timed --waits` (MAME's 68000 at the board's timing) against `tests/harness/slowdown_check` with `slowdown_compare.py`: 100,000 VBLANKs of the simple player (about 29 minutes), every one of the 96,389 frames of the game the same board at the same VBLANK, every interrupt at the same cycle; 3,357 VBLANKs lagged in play on both. Slowdown off: the game exactly as before (30,000 VBLANKs, the same hashes). Replays (`replay_check`, `training_replay_check`) and save states taken in the middle of slow frames (`state_slowdown_check`) play back the same
  - The setting: GAME OPTIONS > SLOWDOWN, on by default (`[game] slowdown`); a replay keeps the one it was recorded with (replay format 3; older replays play with it off, as they were made); changing it during a game stops that game's replay
  - With this weak bot the busiest frame took 802,540 cycles (nearly three frames); a real player at full power sees more slowdown

Found: the patches only point two checks of `$101398` bit 2 elsewhere; `$101398` is the buttons' byte the vblank interrupt makes (player 1's buttons in bits 0-2, player 2's in 3-5), and it clears bit 2: the released game's debug mode is that bit, never set. So the port sets it as the interrupt returns (`program_after_vblank`), in play: the main loop's pause and stage advance, `func_035D78`'s palette editor, object spawner and stage select, and the ship not shot down (`func_02BBF2`). The RAM editor: `$1018E8` = 1. Checked (`tests/harness/debug_check`): no deaths in 2400 frames (3 without), P2 Start pauses, P1 C + Up moves the stage, P1 Start goes on, the RAM editor's flag. Source: sudden-desu.net, "DonPachi debug tools and more"
